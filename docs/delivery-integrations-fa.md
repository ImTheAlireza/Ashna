# گزارش اجرای سرعت زنجیره و اتصال افزونه‌ها — آشنا ۲.۷.۹

۱۴ اکتبر ۲۰۲۶ · این گزارش تفاوت پیاده‌سازی، تست شبیه‌سازی‌شده و تأیید روی سایت واقعی را مشخص می‌کند.

## ۱. تغییرات اجراشده در ارسال

- کلاس `Ashna_Delivery` بودجهٔ مشترک و scope ایمن برای WordPress HTTP ایجاد می‌کند: **۴ ثانیه هر تلاش، ۹ ثانیه کل مسیر SMS/بله**. هر چهار مقدار از تب «پیامک» قابل تغییر و در زمان ذخیره/اجرا محدودسازی می‌شوند.
- درخواست‌های توکن و retry داخلی یک درایور بودجهٔ جدا نمی‌گیرند. مقدار timeout درخواست به زمان باقی‌مانده محدود می‌شود، پس از اتمام بودجه درخواست جدید شروع نمی‌شود و redirectهای HTTP در محدودهٔ ارسال دنبال نمی‌شوند.
- Circuit Breaker پیش‌فرض پس از **۲ خطای ارتباطی/سرور**، مسیر را **۶۰ ثانیه** کنار می‌گذارد. خطاهای HTTP 5xx/429 با observer پاسخ شناسایی می‌شوند؛ خطای شماره، تنظیمات یا پاسخ تجاری نامشخص به‌تنهایی مدار همهٔ کاربران را باز نمی‌کند. خطای PHP درایور به خطای عمومیِ بدون متن محرمانه تبدیل و پشتیبان امتحان می‌شود.
- probe بعد از استراحت با `add_option` و lease غیرautoload هماهنگ می‌شود؛ حذف lease مقایسه‌ای است تا lease درخواست دیگر حذف نشود. lease قدیمیِ درخواست متوقف‌شده قابل بازیابی است. این کنترل probe، سهمیهٔ اتمیک ارسال برای همهٔ درخواست‌ها نیست؛ شمارندهٔ transient تقریبی و قابل بازنشانی توسط cache است.
- کلید سلامت HMAC تنظیمات است؛ شماره یا کلید API در نام transient/option نوشته نمی‌شود. تغییر تنظیمات وضعیت قبلی را جدا می‌کند. تست صریح درگاه توسط مدیر از مدار عبور می‌کند، نه از بودجهٔ زمانی.
- scope در `finally` پاک می‌شود و HTTP خارج از اجرای درایور محدود نمی‌شود. پس از اولین موفقیت SMS، پشتیبان‌ها اجرا نمی‌شوند. حالت صریح «هر دو» هنوز کانال دوم را هم امتحان می‌کند، اما اگر فقط یکی موفق شد، همان کانال در نتیجه و لاگ ثبت می‌شود.

### تجربهٔ کاربری

بعد از ۳ ثانیه پیام انتظار قابل فهم نمایش داده می‌شود. فرم در حال ارسال، درخواست تکراری نمی‌سازد؛ timer پس از پاسخ/خطا پاک و دکمه/spinner بازیابی می‌شوند. AJAX دارای timeout برابر بودجهٔ مسیر + ۳۰ ثانیه است (پیش‌فرض ۳۹ ثانیه). پس از timeout، ارسال خودکار تکرار نمی‌شود و نتیجهٔ احتمالی نامعلوم به کاربر گفته می‌شود؛ timeout مرورگر، پردازش سرور را لغو نمی‌کند.

### مرز عملکرد

این اعداد زمان پیکربندی API هستند، نه ضمانت تحویل پیامک یا حداکثر قطعی پاسخ صفحه. SMTP، SDK مستقل از WordPress HTTP، DNS/transport خاص، کپچا، صف PHP و هاست ممکن است رفتار دیگری داشته باشند. هنوز benchmark واقعی p50/p95/p99 اپراتور نداریم. اگر سرویس ارسال را پذیرفته ولی پاسخ گم شده باشد، failover همچنان ممکن است پیامک/هزینهٔ تکراری ایجاد کند؛ idempotency سراسری ادعا نمی‌شود.

## ۲. اتصال‌های اجراشده

همهٔ اتصال‌ها **اختیاری و پیش‌فرض خاموش** هستند؛ در «آشنا ← احراز هویت ← اتصال ورود حساب‌های موجود» فعال می‌شوند. فرم اصلی افزونهٔ ثالث حذف نمی‌شود؛ فرم `[ashna_otp_login]` را در صفحهٔ ورود مناسب قرار دهید. فعال‌بودن اتصالِ موجود در سایت، ثبت‌نام عمومی آشنا را در درخواست کد، تأیید و خود تابع ثبت‌نام متوقف می‌کند، حتی اگر `auto_register` روشن باشد. این رفتار جلوی دورزدن ثبت‌نام فروشنده/پرداخت/تأیید را می‌گیرد.

### Dokan

با APIهای خود دکان، فروشنده تشخیص داده می‌شود. فروشندهٔ فعال به داشبورد دکان و فروشندهٔ فاقد مجوز فروش به حساب ووکامرس هدایت می‌شود. نقش و `dokan_enable_selling` بازنویسی نمی‌شوند؛ محدودشدن فروش، الزاماً ممنوعیت ورود به خود حساب نیست. مقصد صریح فرم، مقصد دستی و checkout حفظ می‌شوند. آشنا نقش فروشنده نمی‌سازد، onboarding را جایگزین نمی‌کند و فروشندگی را تأیید نمی‌کند.

### Paid Memberships Pro

تابع بومی `pmpro_login_redirect` اجرا می‌شود: مقصد حساب یا انتخاب پلن مطابق رفتار خود PMPro. انقضای عضویت به‌تنهایی مانع ورود برای تمدید نیست؛ کنترل محتوای پولی، وضعیت پلن و پرداخت در اختیار PMPro باقی می‌ماند. دادهٔ عضویت تغییر نمی‌کند.

### Ultimate Member

پیش از صدور کوکی در هر سه مسیر OTP، رمز و Passkey، تابع بومی `um_wp_form_errors_hook_logincheck` وضعیت حساب را بررسی می‌کند. حساب inactive، awaiting_admin_review، awaiting_email_confirmation و rejected رد می‌شود. منع ورود عمومی مدیر و لیست IP/ایمیل مسدود نیز رعایت می‌شوند؛ handlerهای فرم UM که `exit`/redirect می‌کنند مستقیماً روی AJAX اجرا نشده‌اند. مقصد پیش‌فرض، صفحهٔ account است؛ همهٔ redirectهای نقش/فرم UM شبیه‌سازی نشده‌اند.

### MemberPress — تأییدنشده

فقط پل آزمایشی گزینهٔ صفحهٔ حساب `MeprOptions::fetch()->account_page_id` و جلوگیری از ثبت‌نام عمومی پیاده شده است. قرارداد با fixture تست شده، نه کد اصلی MemberPress. **نسخهٔ معتبر در مخزن موجود نیست؛ سازگاری واقعی، افزونه‌های جانبی، تأیید حساب و 2FA قابل تأیید نیستند.** پیش از استفادهٔ عملی، فایل معتبر و نسخهٔ مورد استفاده لازم است.

### اولویت و امنیت

در حالت auto: فروشندهٔ Dokan، سپس PMPro، UM و MemberPress؛ انتخاب صریح معتبر فرم و تنظیمات دستی مقدم‌اند و checkout حفظ می‌شود. سیاست حساب UM مستقل از مقصد اعمال می‌شود. `wp_authenticate_user`، hook اختصاصی احراز و رویداد `wp_login` حفظ شده‌اند؛ OTP/Passkey کل زنجیرهٔ `authenticate` تمام افزونه‌ها را اجرا نمی‌کنند. 2FA و تأییدهای افزونه‌های جانبی نیازمند اتصال/آزمون جدا هستند. redirect مجوز دسترسی نیست.

## ۳. تست‌های قابل بازسازی

- `tests/delivery-integration.php`: **۱۰ سناریو**؛ hook واقعی وردپرس، manager/dispatcher واقعی و در یک سناریو درایور/پارسر واقعی SMS.ir؛ شبکه و ذخیره‌سازی fixture هستند. موفقیت اولیه، failover، مدار باز، تست مدیر، probe هم‌زمان/lease منقضی، بازیابی، بودجهٔ کل، چند درخواست داخلی، پاک‌سازی scope، خطای درایور، تغییر تنظیمات، عدم خراب‌شدن مدار با خطای گیرنده، HTTP 503 و نتیجهٔ ناقص SMS/بله پوشش داده شده‌اند.
- نتیجهٔ نمونهٔ شبیه‌ساز: چهار مسیر با تأخیر فرضی ۵ ثانیه، بودجهٔ هر تلاش ۱ و کل ۳ ثانیه؛ خروجی حدود **۳٫۰۰ ثانیه** و **سه درخواست HTTP**، بدون آغاز ارسال چهارم. این تست از sleep محدودشده با timeout استفاده می‌کند، نه شبکه/اپراتور واقعی؛ اثبات سرعت اینترنت مشتری نیست.
- `tests/ecosystem-integration.php`: چهار گروه تست با توابع واقعی pinned از Dokan، PMPro و UM؛ لایهٔ DB/سرویس‌ها و MemberPress fixture هستند. ۱۲ ترکیب «چهار وضعیت ممنوع UM × سه روش ورود» بدون صدور کوکی رد می‌شوند؛ حساب مجاز، مقصدها، نقش، ثبت‌نام مدیریت‌شده، منع IP/ایمیل/مدیر و redirect خارجی نیز بررسی می‌شوند.
- `tests/slow-delivery-browser.mjs`: Chromium با frontend و jQuery واقعی؛ transport AJAX کنترل‌شده. پیام ۳ ثانیه‌ای، منع دوباره‌فرستی فرم، عدم retry خودکار، بازیابی دکمه و انتقال به مرحلهٔ OTP تست شده‌اند.
- مجموعهٔ ۱۰ سناریوی ارسال و ۴ گروه اتصال، به‌همراه رگرسیون نشست/AJAX، روی PHP source نسخه‌های **7.4، 8.2 و 8.3 پاس شد**. lint هر **۷۶ فایل PHP**، ۲۲ سناریوی bootstrap لایسنس، requirement gate نسخهٔ 8.2، تشخیص فعال‌سازی ۱۳ سناریو + ۱۴ fixture پیام ionCube + ۱۵ سناریوی پیام خصوصی، تست nonce مرورگر و سازگاری هویت نیز پاس شدند.
- راهنمای PDF سه‌صفحه‌ای دوباره رندر شد: بدون سرریز یا برخورد با پاورقی، با فونت/تصویر و اعداد فارسی معتبر. صفحهٔ معرفی در عرض‌های ۳۲۰/۳۹۰/۱۲۸۰ پیکسل و هر دو تم بدون سرریز بررسی شد. بسته‌های نصب شامل همان فایل‌های تست‌شده‌اند و checksumها بررسی شدند.
- رقابت probe با lease ازپیش‌موجود شبیه‌سازی شده، نه تست چندپردازشی با MySQL/Redis واقعی. این تست‌ها بررسی فایل واقعی RTL یا Loader روی هاست نیستند.

### منابع pinned

شناسه‌ها و SHA256 در `tests/fixtures/ecosystem-sources.json` ثبت‌اند؛ منابع ثالث فقط در `.cache` دریافت می‌شوند و داخل ZIP محصول یا Git کپی نشده‌اند. نسخه‌ها از سربرگ snapshot منبع هستند، نه تضمین همهٔ انتشارهای آن محصول:

- [Dokan 5.3.0، snapshot 63ad893](https://github.com/getdokan/dokan/blob/63ad8935357869a4743a5aa8a8c7fc0bc7bd1754/includes/functions.php): تشخیص فروشنده، وضعیت فروش و URL داشبورد.
- [PMPro 3.8.9، snapshot d95654d](https://github.com/strangerstudios/paid-memberships-pro/blob/d95654dd3b2a45c42f5bb976271061eb41a304f8/includes/login.php): تابع redirect بومی ورود.
- [UM 2.14.0، snapshot 0ffe1ef](https://github.com/ultimatemember/ultimatemember/blob/0ffe1ef917fb45810aa756b9064e9ffdcf436e3c/includes/core/um-filters-login.php): سیاست وضعیت حساب پیش از نشست.

دستورهای زیر از ریشهٔ مخزن اجرا می‌شوند؛ خود تست‌ها داخل ZIP نصب محصول قرار ندارند.

```sh
python tests/prepare-session-tests.py
python tests/prepare-ecosystem-tests.py
python tests/run-delivery-ecosystem.py
python tests/run-session-integration.py
ASHNA_BUNDLED_LIBS=1 node tests/slow-delivery-browser.mjs
ASHNA_BUNDLED_LIBS=1 node tests/post-login-nonce.mjs
```

`PHP_BINARY` را می‌توان به PHP CLI یا php-wasm-cli و `PHP` را برای WASM به 7.4/8.2/8.3 تنظیم کرد. منابع نسخهٔ لایسنس‌دار همچنان حداقل PHP 8.2 دارند؛ اجرای تست source روی 7.4، تأیید اجرای لایسنس روی آن نیست.

## ۴. آنچه هنوز لازم است

- **فایل معتبر MemberPress** برای تکمیل و تأیید adapter؛ هیچ نسخهٔ غیرمجاز یا لایسنس ساختگی استفاده نشده است.
- تست staging یک نصب کامل با نسخه‌ها و افزونه‌های جانبی واقعی: فرم ورود/ثبت‌نام، checkout، onboarding، تأیید مدیر، 2FA، تعلیق، تمدید، مالکیت سفارش، logout، cache و شمارهٔ حساب‌های قبلی.
- تست مجاز هاست/درگاه واقعی و اندازه‌گیری زمان پاسخ و تحویل؛ تنظیم ۴/۹ ثانیه نقطهٔ شروع است و برای هر ارائه‌دهنده باید بررسی شود.
- سهمیهٔ اتمیک/بودجهٔ هزینه، تأیید OTP داخل ثبت‌نام تخصصی و idempotency سرویس‌دهندگان در این نسخه ساخته نشده‌اند.
- فایل رسمی RTL همچنان در مخزن نیست و هش/هویت/شرط لایسنس دست‌نخورده مانده؛ بستهٔ بدون لایسنس جداست.
