# بررسی نشست، JWT و دسترسی پس از ورود

آشنا / Ashna · نسخهٔ اصلاح‌شدهٔ **۲.۷.۸** · ۱۴ اکتبر ۲۰۲۶

## نتیجهٔ بررسی

انتقاد دربارهٔ نبود توضیح مدیریت نشست در معرفی محصول وارد بود؛ اما به معنی فقدان نشست استاندارد در کد نبود. نسخهٔ قبلی OTP از `wp_set_current_user()`، `wp_set_auth_cookie()` و رویداد `wp_login` استفاده می‌کرد و نقش کاربر موجود را هنگام ورود تغییر نمی‌داد.

**برای افزونه‌ای که در همان سایت وردپرس/ووکامرس کار می‌کند، JWT جداگانه لازم نیست.** آشنا از نشست و کوکی هستهٔ وردپرس استفاده می‌کند. اضافه‌کردن JWT موازی بدون نیاز API، دو منبع مستقل برای هویت، انقضا و خروج ایجاد می‌کند و می‌تواند هماهنگی را بدتر کند.

در بررسی کد چند نقص واقعی پیدا و اصلاح شد:

| موضوع | وضعیت قبلی | اصلاح نسخهٔ ۲.۷.۸ |
|---|---|---|
| نشست وردپرس | استاندارد، ولی کد تکراری در سه مسیر | مسیر واحد `Ashna_Session::login()` برای OTP، رمز عبور و Passkey |
| نشست مهمان ووکامرس | اتکا به تشخیص ورود در درخواست بعدی | فراخوانی API عمومی `init_session_cookie()` روی session فعال، مطابق مرحلهٔ نشست در helper رسمی ووکامرس |
| nonce بعد از ورود AJAX | nonce مهمان در JavaScript باقی می‌ماند | تولید nonce با توکن نشست تازه و انتقال آن به صفحه قبل از ثبت فوری Passkey |
| سیاست حساب کاربری | بررسی‌های استاندارد حساب در مسیرهای دستی فراخوانی نمی‌شد | رعایت `wp_authenticate_user`، بررسی spam در multisite و فیلتر اختصاصی روش ورود |
| موفقیت کاذب | در صورت منع ارسال کوکی، پاسخ می‌توانست موفق باشد | رد ورود، حذف فقط توکن تازهٔ ناموفق و بازگرداندن current user قبلی |
| نقش ثبت‌نام عمومی | UI فقط دو نقش داشت، ولی تنظیم واردشده/نقش پیش‌فرض سایت می‌توانست نقش دیگری بدهد | allowlist نقش‌های customer/subscriber در ذخیرهٔ تنظیمات و مسیر ثبت‌نام؛ بدون fallback به نقش مدیریتی سایت |
| Passkey بدون OpenSSL | نبود تابع بررسی امضا باعث رد صریح ورود نمی‌شد | رد اجباری ورود در نبود OpenSSL و در هر نتیجهٔ بررسی امضا غیر از موفقیت قطعی |
| redirect مسیر Passkey | مسیر مستقل با پذیرش redirect درخواست | استفاده از resolver مشترک و `wp_validate_redirect()` برای مقصد ارسالی مرورگر |
| storage مرورگر | خواندن localStorage ممکن بود رابط موفقیت ورود را متوقف کند | تحمل مسدودبودن storage بدون توقف ورود یا هندآف nonce |

## معماری نشست پس از تأیید هویت

۱. ابتدا کد OTP، رمز یا امضای Passkey بررسی می‌شود. هیچ نشست موفقی پیش از عبور از این مرحله ایجاد نمی‌شود.
۲. حساب WordPress معتبر و سیاست‌های حساب بررسی می‌شوند؛ خروجی فیلتر نمی‌تواند حساب دیگری را جایگزین کند.
۳. `wp_set_current_user()` هویت جاری درخواست را به همان حساب می‌برد.
۴. `wp_set_auth_cookie()` نشست جدید را با `WP_Session_Tokens` هسته می‌سازد. کوکی اختصاصی، session PHP و JWT موازی ساخته نمی‌شوند.
۵. هسته، امضا، زمان انقضا و ویژگی‌های امنیتی کوکی را مدیریت می‌کند. صدور کوکی تابع SSL سایت و فیلترهای استاندارد وردپرس است؛ کوکی ورود توسط هسته HttpOnly است.
۶. اگر ووکامرس session فعال با API عمومی مربوطه داشته باشد، انتقال نشست مهمان با همان handler خود ووکامرس انجام می‌شود؛ افزونه جدول session ووکامرس را مستقیماً تغییر نمی‌دهد. اگر session هنوز مقداردهی نشده باشد، چرخهٔ عادی ووکامرس در درخواست بعدی مسئول بارگذاری آن است.
۷. رویداد `wp_login` با `user_login` و شیء واقعی `WP_User`، یک بار اجرا می‌شود. handler استاندارد ووکامرس از همین رویداد، بازیابی/ادغام سبد ذخیره‌شده را برای درخواست بعدی علامت می‌زند.
۸. کوکی تازه در حافظهٔ همان درخواست نیز در اختیار هسته قرار می‌گیرد تا `wp_create_nonce()` توکن نشست جدید را ببیند. فقط nonce به JavaScript برمی‌گردد؛ مقدار کوکی و session token در JSON برگردانده نمی‌شود.
۹. در درخواست بعدی، هسته از روی کوکی امضاشده همان کاربر و نقش‌ها را بازسازی می‌کند. خروج و ابطال نشست نیز از API استاندارد وردپرس پیروی می‌کند.

رفتار فعلی «مرا به خاطر بسپار» مانند نسخهٔ قبلی فعال است. زمان پیش‌فرض آن را هسته تعیین می‌کند و فیلتر `auth_cookie_expiration` رعایت می‌شود. ورود مجدد توکن تازه می‌گیرد، ولی تمام نشست‌های دستگاه‌های دیگر را خودسرانه باطل نمی‌کند؛ این سیاست را APIهای مدیریت نشست وردپرس تعیین می‌کنند.

## نقش، Permission و سفارش‌های ووکامرس

- نقش‌ها و capabilityهای کاربر موجود در ورود OTP/Passkey/رمز بازنویسی نمی‌شوند. مشتری، مدیر فروشگاه و مدیر سایت همان دسترسی قبلی را دارند.
- مجوزها باید در سمت سرور با `current_user_can()` و APIهای مجوز ووکامرس بررسی شوند؛ شناسهٔ کاربر یا nonce برگشتی به مرورگر، مجوز دسترسی به سفارش دیگران نیست.
- permissionهای مالکیت سفارش ووکامرس از همان WP user ID استفاده می‌کنند. تست بررسی می‌کند مشتری سفارش متعلق به خود را ببیند ولی مجوز سفارش مشتری دیگر را نگیرد.
- فقط در ایجاد حساب جدید، نقش انتخاب می‌شود: customer در صورت وجود این نقش، یا subscriber. نقش مدیریتی/ناشناخته از تنظیم واردشده پذیرفته نمی‌شود. نبود نقش امن به خطای ثبت‌نام منجر می‌شود، نه اعطای دسترسی بیشتر.

## افزونه‌های امنیتی و معماری API

`wp_authenticate_user` و بررسی spam اجرا می‌شوند. افزونه‌های دارای سیاست ورود بدون رمز می‌توانند از `ashna_authenticate_user` استفاده کنند؛ آرگومان دوم، `otp`، `password` یا `passkey` است و بازگرداندن `WP_Error` ورود را رد می‌کند.

این به معنی تضمین سازگاری با تمام افزونه‌های 2FA، ورود سازمانی یا مسدودسازی حساب نیست. callbackهایی که فقط به زنجیرهٔ احراز رمز یا فرم خاص وردپرس متصل‌اند، لزوماً جریان OTP را نمی‌شناسند و باید جداگانه بررسی شوند. برای سایت اصلی، همان ترکیب افزونه‌های امنیتی باید روی staging آزمایش شود.

این پیاده‌سازی، ورود first-party وردپرس است؛ احراز API مستقل برای اپ موبایل/headless، refresh token، OAuth یا JWT بین چند دامنه در این نسخه ارائه نشده است. آن کاربردها به طراحی و اعتبارسنجی جداگانه نیاز دارند.

## تست‌های انجام‌شده

تست‌ها از کدهای رسمی **WordPress 6.8.3** و **WooCommerce 9.9.5** استفاده می‌کنند، نه نسخهٔ دست‌نویس APIهای حساس:

- `WP_User`، نقش‌ها/capabilityها، کوکی auth، `WP_Session_Tokens`، تولید و اعتبارسنجی nonce و ابطال نشست واقعی هسته.
- handler واقعی session ووکامرس و تابع واقعی permission مالکیت سفارش و علامت‌گذاری سبد ذخیره‌شده.
- مسیرهای واقعی AJAX افزونه برای OTP، رمز و Passkey؛ در تست Passkey از امضای واقعی EC استفاده می‌شود و فقدان OpenSSL در یک اجرای جدا با غیرفعال‌کردن تابع بررسی امضا آزموده می‌شود.
- nonce مهمان پس از ورود دیگر مجاز نیست؛ nonce تازه در همان درخواست و درخواست بعدی معتبر است و endpoint ثبت Passkey آن را می‌پذیرد.
- هویت مشتری و کارکنان، ورود تکراری/تعویض حساب، دسترسی سفارش خود/دیگران، توکن تازه، انقضای نشست، کوکی دستکاری‌شده و ابطال نشست.
- انتقال سبد مهمان و روش ارسال به session مشتری و حفظ آن در نمونهٔ درخواست بعدی.
- رد حساب توسط policy، جلوگیری از جایگزینی حساب در فیلتر، منع کوکی، هدر ارسال‌شده و عدم باقی‌ماندن توکن ورود ناموفق.
- اجرای JavaScript واقعی افزونه با jQuery در Chromium: nonce درخواست ورود، سپس nonce authenticated در درخواست ثبت Passkey، با localStorage عادی و مسدود.

**محدودیت:** دیتابیس، object cache، دادهٔ سفارش، درگاه ارسال OTP و انتقال JSON در تست‌ها fixture هستند؛ WordPress/WooCommerce کامل روی هاست زنده، مرورگر با کوکی واقعی شبکه، checkout/درگاه پرداخت، Redis واقعی، فایل رسمی لایسنس و تمام افزونه‌های ثالث آزمایش نشده‌اند. این گزارش، ممیزی جامع امنیت WebAuthn یا گواهی سازگاری تمام نسخه‌ها نیست.

فرمان‌های بازتولید در `tests/README.md` ثبت شده‌اند.

## چک‌لیست سایت مقصد

- HTTPS، نشانی WordPress و Site URL و تشخیص SSL پشت reverse proxy درست تنظیم شوند؛ تشخیص SSL نباید به هدر قابل جعل اعتماد کند.
- پاسخ `admin-ajax.php` و صفحات حساب/سبد/checkout به‌اشتباه توسط CDN/full-page cache ذخیره نشوند. کوکی ورود وردپرس باید باعث bypass کش حساب شود.
- بعد از نصب نسخهٔ تازه، کش صفحه/CDN/مرورگر پاک شود تا JavaScript و nonce قدیمی باقی نماند.
- ورود با حساب قدیمی مشتری و کارکنان، ثبت فوری Passkey بعد از OTP، خروج و ورود مجدد، سبد مهمان و مالکیت سفارش روی staging تست شوند.
- افزونه‌های امنیتی و 2FA واقعی سایت، تنظیمات Secure cookie و مسیرهای چنددامنه/زیرپوشه جداگانه بررسی شوند.
